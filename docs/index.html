Opening demonstration

GitHub carries the
whole engineering loop.

  • An issue names intent.
  • A pull request makes work reviewable.
  • Checks and people decide what ships.

Watch the facilitator open a prepared synthetic pharmacy instructor station. A request to prevent overselling after consecutive reservations becomes a GitHub issue with acceptance criteria. A test-only change is proposed in a pull request. Actions runs service tests independently of any agent. A reviewer decides whether to accept the change; a separate release decision would need its own revision-bound evidence.

  1. Open the station issue and identify the need, owner and acceptance criteria.
  2. Open its linked pull request and inspect the proposed diff and review.
  3. Open the Actions checks and distinguish a passing test from an agent's claim.
  4. Inspect security evidence, the release boundary and the named next decision.

Expected outcome: you can trace intent, proposal, independent verification and human authority through durable GitHub artifacts. A green check does not itself deploy anything. The five labs build and inspect these same boundaries in your own station.

Live path: the facilitator rehearses this chain in a separate instructor station and shows its actual GitHub issue, pull request, checks and review. If the live chain is unavailable, inspect the local synthetic stock tests as an illustrative source example, plus Lab 4's labelled historical security observation. They are not one live chain and do not prove a deployment. GitHub Agentic Workflows are public preview; no preview run is required for this opening.

The loop reads back
before acting again.

  • Persist what happened.
  • Compare the next signal.
  • Retry, wait, escalate or stop.

The operating sequence is intake, delegate, act, verify, persist and decide. GitHub holds the issue, pull request, checks and decision record. Copilot is the primary worker; deterministic checks and required human review remain separate authorities. Per-run limits reduce exposure but cannot prevent duplicate work across runs without stable identity and a read-back of earlier evidence.

The sandbox path needs no dedicated enterprise organization. Enterprise policies, security licensing and environment approvals require a capability check; unavailable controls have labelled lab fallbacks and are never presented as active enforcement.

Adoption roadmap

Start where outcomes
can be verified.

  • Choose reversible, low-risk work.
  • Name the accountable owner.
  • Measure accepted outcomes and cost.

Choose a frequent task with clear acceptance, quick tests and reversible changes. Agree who owns the issue, agent permissions, review, release and stop decision. Track accepted outcomes, time spent on human attention, duplicate avoidance, failure handling and cost over four to eight weeks. If moving from Azure DevOps, migrate repositories and pipelines in bounded waves; verify identity, policy and evidence parity before retiring existing controls.

Carry one verified result and an accountable next decision from each chapter into the next.
