Before you start

One workflow. Four edits.
One reviewable change.

  • Tools and permissions must describe the same scope.
  • Budget is part of the contract.
  • A green check is the proof, not your opinion.

Outcome: a reviewable pull request that proposes a narrower repository-pulse contract. It is not an executable change until the generated lock workflow is compiled, committed and checked against that source.

You need

Your station repository
The URL was sent with your preparation message. You have write access to it. Everything in this lab happens there.
A browser
The whole lab can be completed in the GitHub web editor. A local clone and the gh CLI are optional.
Nothing else
No local Node.js, no extension and no model entitlement are required to finish the core path.

Warning

Product state: GitHub Agentic Workflows are public preview. The station CI runs service tests; it does not compile agentic workflow sources or verify their lock files. The core path is a source review on a branch. Only merge or run the new contract when a facilitator with the approved compiler has committed and validated its lock file. Otherwise use the source-based fallback; do not claim you ran the changed workflow.

Starting state

Your repository already contains .github/workflows/repository-pulse.md. The frontmatter is the contract; the prose below it is the instruction. As shipped, the contract is deliberately too wide.

Boundary, key, and value as shipped

Trigger

Key: on

As shipped: workflow_dispatch — a person starts it.

Read scope

Key: permissions

As shipped: contents, issues, pull-requests, actions, all read.

Model access

Key: copilot-requests: write

As shipped: Inference through the per-run token. This is not permission to write repository content.

Network

Key: network

As shipped: defaults — an allow-list, not open egress.

Write scope

Key: safe-outputs

As shipped: Owned create-issue and update-issue, maximum one of each per run.

Agent budget

Key: timeout-minutes, max-ai-credits

As shipped: 10 minutes and 100 AIC. The threat detector has its own 20 AIC cap.

The agent never receives a general-purpose write token. Those two safe-output types are the only ways anything leaves the run. The caps are per output type and per run — they are not one global transaction, and they do not deduplicate across runs.

Narrow the contract

Start on a branch.

  • Never assume branch protection.
  • Review is where the change is judged.

In your station repository, open the branch selector, type the branch name and choose Create branch:

narrow-repository-pulse

Prefer the command line? This is equivalent:

gh repo clone <your-station-repository>
cd <your-station-repository>
git switch -c narrow-repository-pulse

Rule

Do not commit to the default branch. The facilitator checks whether protection is enforceable for this station; Chapter 3 distinguishes an enforced rejection from a labelled demonstration.

Align tools with permissions.

  • Remove the scopes you no longer read.
  • Cut time and inference budget.
  • Keep the safety invariants untouched.

Your team has decided this automation should review issues only, and cost less. Open .github/workflows/repository-pulse.md on your branch and make exactly these four edits.

Edit 1 — Match tools to permissions

Delete pull-requests: read and actions: read from permissions. Under tools.github, replace toolsets: [default] with:

toolsets: [repos, issues]

A toolset wider than the permission grant is a silent contradiction. Reviewers cannot tell what the automation is actually allowed to touch.

Edit 2 — Reduce the time budget

timeout-minutes: 5

Edit 3 — Reduce the inference budget

max-ai-credits: 40

Edit 4 — Narrow the instruction

Replace the opening instruction line with:

Review issues opened or closed in the previous seven days. Read repository files only to explain issue context.

Then replace the bullet - failing or cancelled default-branch checks; with:

- issues opened or closed in the period, each linked to its artifact;

Rule

Do not change these. Keep copilot-requests: write — it grants model access, not repository writes. Leave the manual trigger, the Copilot engine, network: defaults, both owned safe-output limits of one, the concurrency group, and the untrusted-input paragraph exactly as they are. Keep the threat detector at 20 AIC with continue-on-error: false: a failed security review must stop the run, not warn and proceed.

Commit to your branch with a message that states the intent, for example Narrow repository pulse to issue review.

Prove it on GitHub

Source is not the lock.

  • Review the proposal in a pull request.
  • Compile before any merge or run.

Open a draft pull request from narrow-repository-pulse into the default branch. The station's Test service check runs automatically; it does not validate this workflow edit. Review your source diff against the reference contract and have a partner identify the remaining read scopes, safe outputs and budget. A green service test is not approval to merge a stale lock file.

Checkpoint — the executable boundary

Open .github/workflows/repository-pulse.lock.yml on the default branch. It still reflects the old source. Keep this pull request in draft unless a facilitator can compile your branch with the approved gh aw version, commit the changed lock file to the same pull request, and verify the compiled workflow against the edited source. Read the resulting lock diff and repeat the review before merging. If that capability is unavailable, leave the source proposal open and move to Lab 2; do not run the old lock as proof of your edits.

If compilation is available

Have the facilitator compile this branch's source with gh aw compile --dir .github/workflows --validate in a checkout of your station repository, then commit the regenerated .lock.yml on your branch. Resolve toolset, permission or YAML errors before requesting merge. If compilation or validation fails, the draft stays open.

Request a review from your table partner. Ask them one question: after this change, what is the worst thing this automation can still do? The intended answer is "create or update one issue it owns" per run, but the old lock remains executable until recompilation and merge. If they cannot tell from the diff alone, the proposal is not narrow enough yet.

No signal can mean no-op.

  • Per-run caps are not deduplication.
  • Reconciliation may produce no issue.

Only after the compiled lock is reviewed and merged, and preview is enabled, go to Actions, select Repository pulse and choose Run workflow. It is a manual trigger. The seeded backlog may be older than its seven-day window; no actionable change correctly produces a no-op. Do not invent a signal or weaken the no-op rule just to obtain an issue.

If the run publishes an owned issue for a real eligible signal, check three things:

  1. The issue is owned by the workflow — it carries the <!-- workshop-pulse:v1 --> marker.
  2. It links each finding to an artifact, so a reader can verify the claim rather than trust it.
  3. It ends with a next decision, not just a summary.

Now find what is missing

Run the workflow a second time without changing anything in the repository.

An identical run should produce no new issue update under the source's reconciliation instructions; inspect the run's no-op explanation. This is instruction-level reconciliation, not a deterministic pre-delegation gate: inference can still run, and ambiguous or truncated reads should block rather than publish. The per-run cap bounds one run but cannot prove cross-run deduplication. Robust recurrence needs:

Stable work identity
Something that says "this is the same piece of work as last time", independent of the run number.
Prior-state read-back
Reading what the previous run concluded before deciding to act again.
An explicit next decision
A justified no-op is a valid, accountable outcome. Silence is not.

Chapter 5 closes exactly this gap. Carry the observation with you.

Recovery and extensions

Recovery is planned.

  • The reference contract resets the edits.
  • A draft PR is a valid stopping point.

Common blockers

SymptomLikely causeFix
Test service is green but no lock file changed.The station CI tests the application, not the agentic workflow contract.Leave the PR in draft. Ask the facilitator to compile and validate your source, or continue with source review only.
The facilitator's compile fails with a toolset or permission error.The source's grants or YAML do not match the desired contract.Compare your source with the reference; fix the same branch and compile again.
No Test service check appears on the pull request.Actions are disabled or the PR does not target the default branch.Retarget the pull request and ask the facilitator to confirm Actions availability.
Your push is rejected.Protection may be active or your permissions are insufficient.Verify your branch and permissions; do not assume this is proof of default-branch protection.
Run workflow is missing in Actions.The validated lock has not merged, or preview is not enabled.Keep the PR in draft and use the source-based fallback below.
The run stops at threat detection.The detector rejected the output, which is the intended stop.Read the detector log and keep continue-on-error: false. Do not raise budgets or weaken the detector to get a green run.

Catch up or reset

You ran out of time on the edits
Copy the reference contract over your file, commit, and continue from Step 3. Keep the PR in draft until a validated lock accompanies it.
The compiler or preview engine is unavailable
Keep the source-only PR open. For Step 4, compare the old lock file with the proposed contract: identify the owned issue marker, per-run safe-output caps and missing deterministic prior-state gate. Treat these as source properties, not evidence of an executed run. Carry the continuity question to Lab 5.
You edited the wrong branch
Nothing is lost. Create the branch again from the default branch and redo the four edits; they take two minutes the second time.
You want to start over completely
Close your draft pull request and delete its branch after confirming the default branch was not changed. Never assume protection was active without a rejection probe.

Go further
after the core review.

  • Compile before applying a contract.
  • Argue whether it deserves a schedule.

Break it on purpose
On a separate branch, propose contents: write in permissions. Explain why that violates least privilege; do not merge or execute it.
Tighten the trigger
Add a schedule alongside workflow_dispatch. Then argue the other side: what does a schedule create that a manual trigger does not, and does this automation currently deserve it?
Read the lock
If the facilitator compiles your branch, compare the regenerated .lock.yml with the old version and identify the new budgets. Anything not expressed in the reviewed lock is not enforced at runtime.

A narrow source contract makes an automation reviewable; only a compiled, validated lock and human review make it ready to merge. A green service test alone cannot authorize the changed workflow.

Bound it first.
Then let it run.
