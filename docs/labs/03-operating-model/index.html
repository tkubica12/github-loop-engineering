Before you start

Governance must leave evidence.

  • Ownership appears in CODEOWNERS.
  • Stop authority appears in rejection.
  • Decisions survive as repository history.

Outcome: a pull request that names a workflow owner and a governance decision record in your station repository. Where branch protection is confirmed active, capture a real direct-push rejection; otherwise document the missing control and observe an instructor's labelled protected-station demonstration if available.

Time: plan for 20 minutes of guided work inside the 55-minute operating-model chapter. Keep discussion short until the decision record exists.

You need

Your station repository
Use the prepared repository from your instructor. You have write access; ask whether the default branch has enforceable protection before attempting the push probe.
A named reviewer
Use the GitHub user or team name assigned by your instructor. Do not invent an enterprise team in the sandbox profile.
PowerShell and Git
Use PowerShell for the direct-push probe. The browser is enough for the pull requests.

Profile honesty

The sandbox profile creates private repositories under a personal account by default. Protection and required code-owner review depend on the account's plan and repository settings; a CODEOWNERS file alone does not enforce review. If the facilitator cannot confirm enforcement, do not perform the push probe or call a requested reviewer a required reviewer. Enterprise-wide policies, organization budgets and internal visibility are not applied in the sandbox. The enterprise profile remains configurable with remote provisioning disabled.

Starting state

Your repository already contains .github/CODEOWNERS, workflows, agentic workflow files and starter pharmacy code. Branch-protection rules are configured separately, if your station supports them. The ownership file covers broad areas, but the workflow contract and CI workflow need a named accountable reviewer.

Open the two reference artifacts before you start: CODEOWNERS reference and governance decision template.

Make ownership enforceable

Read the current owners first.

  • Find broad ownership.
  • Find missing named workflow accountability.
  • Change the durable control, not notes.

Open .github/CODEOWNERS on the default branch of your station repository. Read it as a control, not documentation.

Identify three things:

  1. Who owns /src/?
  2. Who owns repository instructions such as /AGENTS.md?
  3. Which named reviewer owns .github/workflows/?

The gap is the third answer. Agentic workflow contracts and CI workflows decide what automation may run, what evidence is required, and which token boundaries exist. They need a named accountable reviewer.

Checkpoint

Say the gap in one sentence: "Workflow contracts can change without a named workflow owner reviewing them." If your station already has a workflow owner, verify that it is a real user or team and continue.

Put authority in CODEOWNERS.

  • Check default-branch enforcement.
  • Add workflow-specific ownership.
  • Open a reviewable pull request.

Create a branch named lab-03-workflow-ownership. Edit .github/CODEOWNERS on that branch.

Add a specific workflow rule after the broad /.github/ rule, using the reviewer assigned by your instructor:

/.github/workflows/ @named-reviewer-or-team

If your station uses one named maintainer instead of a team, use that person's GitHub handle. If your future enterprise profile uses teams, record the team name as configurable, not hard-coded.

Open a pull request into the default branch. Title it:

Require a named owner for workflow contracts

Use the pull request body to explain the control: workflow and agentic workflow changes now require the named reviewer before merge.

Rule

The last matching CODEOWNERS pattern wins. Keep the workflow-specific rule after the broad /.github/ rule so workflow ownership is explicit.

Check whether ownership
is enforced.

  • CODEOWNERS names reviewers.
  • Protection determines merge authority.
  • Never assume enforcement.

Open the pull request checks and review box. Verify whether GitHub requests the named reviewer or actually requires that review under active branch protection. Capture the exact wording in your notes.

Where required code-owner review is enabled and enforced, the pull request cannot merge until the required reviewer approves it, unless a configured bypass actor uses their authority. Where it is unavailable, request a partner's voluntary review and mark the control as not enforced in your decision record.

Ordinary writer
Can propose the change but cannot bypass required review.
Named code owner
Can approve the owned path when policy allows.
Ruleset bypass actor
Can bypass only if explicitly configured and auditable.
Enterprise policy owner
Sets higher-level limits in the enterprise profile, not in this sandbox lab.

If review does not appear

Some stations evaluate CODEOWNERS from the base branch. Merge the ownership PR with instructor help, then open a small probe PR that changes only a comment in .github/workflows/ci.yml. If the review is still not required, record the capability gap; do not report it as enforcement.

Observe stop authority

Protection is real when it says no.

  • Verify enforcement before a push.
  • Copy the rejection if tested.
  • Record a missing control honestly.

Safety gate: Ask the facilitator to confirm, from this repository's GitHub settings and an earlier harmless rejection, that protection is active and enforced for your account. If they cannot, skip this push entirely. In an instructor station with verified protection, the facilitator may show their own rejected push as a labelled demonstration; it is not proof about yours. If protection is confirmed for your station, use PowerShell and replace <station-repository-url> with your repository URL.

git clone <station-repository-url>
Set-Location .\<station-repository-name>
git switch main
"lab 03 push probe" | Set-Content .\lab-03-direct-push.txt
git add .\lab-03-direct-push.txt
git commit -m "Probe default branch protection"
git push origin main

Expected result only for a protected station: GitHub rejects the push. Copy the exact remote rejection message into your notes. If it succeeds unexpectedly, stop, notify the facilitator and record the missing control. Do not describe that station as protected.

Only after a rejected push, reset this freshly cloned local probe before doing anything else. If the push unexpectedly succeeded, do not run the reset as though it cleaned the remote; ask the facilitator to coordinate a reviewed revert of the default-branch change:

git fetch origin
git reset --hard origin/main
Remove-Item .\lab-03-direct-push.txt -ErrorAction SilentlyContinue

Rule

Do not ask an instructor to bypass this rejection. The point is to prove that write access is not the same as merge authority.

Commit the operating model

Decisions become durable artifacts.

  • Use the empty template.
  • Answer seven governance questions.
  • Merge through review, not memory.

Create a branch named lab-03-governance-decisions. Copy the decision template into your station repository as:

docs\governance-decisions.md

Fill in the seven headings with your team's decisions. Keep each answer short and specific enough that a reviewer can accept or challenge it.

  1. Who owns the workflow contract?
  2. Who approves production release?
  3. Who sets the budget?
  4. Where does each control live: repository, organization, or enterprise?
  5. What happens when an agent proposes a security-sensitive change?
  6. Who can bypass, and how is bypass audited?
  7. What triggers escalation?

Open a pull request titled Record operating model decisions. Reviewers should reject vague answers such as "the team" when a named role, team or policy owner is required.

Checkpoint

The decision record is not pre-filled guidance. It is your team's committed operating model for this station.

Connect decisions to durable scope.

  • Repository controls travel with code.
  • Organization controls classify repositories.
  • Enterprise controls set the baseline.

Before merging the decision record, add one table that maps each decision to its durable scope and Azure DevOps migration wave.

Repository

Good fit: CODEOWNERS, instructions, workflows, required checks, environments.

Avoid: restating enterprise policy in prose.

Organization

Good fit: repository classes, rulesets, teams, budgets, reusable workflows.

Avoid: making one-off exceptions the default.

Enterprise

Good fit: identity, global AI policy, Actions policy, security baseline.

Avoid: application-specific implementation rules.

Pull request

Good fit: change evidence, review, exception decision.

Avoid: permanent policy that disappears after merge.

Use these migration waves:

Wave one
Git history, repository ownership, deterministic checks and CODEOWNERS. Validate imported branches and tags before redirecting developers.
Coexistence window
Keep Azure Boards, package feeds and some pipelines stable while GitHub pull requests prove the new evidence chain.
Later waves
Convert pipelines with review, re-establish deployment identity with OpenID Connect, and move secrets only when environment approval is ready.

Merge the decision record after review. The lab is complete when the repository contains the merged record and your notes contain either your station's actual rejection or a clearly labelled enforcement gap and instructor demonstration.

Recovery and extensions

Recover without pretending.

  • Use reference artifacts for speed.
  • Label sandbox limits plainly.
  • Never call a simulation live control.

Common blockers

You cannot find the named reviewer
The prepared user or team may not have access. Ask the instructor for the actual reviewer; do not create a fake enterprise team.
The required-review box is missing
Code-owner review may be unavailable, disabled, or awaiting a merged base-branch CODEOWNERS file. Merge the ownership PR first, then try a workflow probe PR. If enforcement remains unavailable, request voluntary review and record the gap.
The direct push unexpectedly succeeds
The earlier protection check was incorrect or bypassed. Stop and tell the instructor. Record the missing control, not a rejection; do not repeat the probe. Coordinate a reviewed revert of the remote change.
A later pull or push fails after the rejected probe
The rejected commit may still be on your local default branch. Run the reset commands in Step 4 on the fresh probe clone only. They remove the local commit, not any remote change.
Placeholders remain in the committed record
Replace every placeholder with a real station user or team, then commit again on the same branch.

Catch up

You need to catch up
Use the CODEOWNERS reference and the decision template. Replace placeholders with real station names before committing.

Extend after the record merges.
