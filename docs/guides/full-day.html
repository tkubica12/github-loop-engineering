Executive platform briefing

The day follows one loop.

  • Capture intent in GitHub.
  • Delegate within explicit limits.
  • Decide from persisted evidence.

The workshop begins with the complete Loop Engineering picture: prompt, context, harness, loop, evidence, and stop condition. The point is not to tour features. The point is to keep intent, proposed change, automated checks, review, release evidence, and follow-up in one traceable system.

GitHub Copilot is the primary coding harness in this workshop. External harnesses such as Claude Code or OpenCode can be discussed as optional execution boundaries, but they do not inherit identical permissions, interfaces, security properties, or availability.

Use the Loop Engineering reference for the longer vocabulary and the architecture guide for the control-plane view.

See it, work with it, connect it.

  • Demos show the complete loop.
  • Labs give one durable outcome.
  • Discussion maps adoption constraints.

See it shows a polished end-to-end outcome, including steps that are too slow, permission-sensitive, or fragile to rebuild live. Work with it gives you one meaningful action in your station repository. Connect it turns the action into an operating model.

The rhythm matters because reasoning-based automation is only useful when it is bounded by deterministic controls and human authority. You should always know what the agent may read, what it may write, what evidence gates it, and who owns the next decision.

Bounded continuous AI

Automation starts with a contract.

  • Tools and permissions must align.
  • Budget is a safety boundary.
  • Output must be owned and capped.

Natural-language automation becomes reviewable only when its contract is concrete. Chapter 1 focuses on trigger, read scope, model access, network policy, safe outputs, time budget, inference budget, and the instruction boundary around untrusted repository content.

The hands-on work narrows a repository pulse workflow so it reviews issues only, spends less, and still publishes only bounded owned issue output. The green check is the proof that the source and generated execution contract agree.

Product state

GitHub Agentic Workflows are public preview. The lab states which parts are ordinary GitHub work and what to read when preview execution is unavailable for your station.

Open Lab 1

A cap is not continuity.

  • Per-run limits bound blast radius.
  • They do not deduplicate work.
  • State makes recurrence accountable.

A per-run limit prevents one run from creating unlimited output. It does not prove that the next run understands prior work, avoids duplicates, or knows when a justified no-op is the correct outcome.

Continuous AI needs stable work identity, prior-state read-back, and an explicit next decision. Chapter 5 returns to that requirement after you have produced the evidence that a real loop must consume.

Verified handoff

Intent must become acceptance.

  • Issues capture business meaning.
  • Specifications remove guesswork.
  • Tests judge the proposal.

The pharmacy scenario asks for a safe stock suggestion when the requested medicine is unavailable. The requirement is deliberately small, but the engineering pattern is broad: write observable acceptance before any worker changes code.

The lab turns the request into a structured issue, a lightweight specification, a bounded proposed implementation, and a pull request that must satisfy deterministic acceptance and regression checks. A suggestion remains a suggestion: it reserves nothing until a person chooses the alternative.

Open Lab 2

A proposal is still untrusted.

  • Review changed scope.
  • Read the diff.
  • Bind handoff to a revision.

Copilot can accelerate the implementation, but the platform still treats the proposal as untrusted. The evidence you want is scope control, passing tests, explainable diff, and a pull request that another person can review without reading an agent transcript.

The durable handoff is not a chat summary. It is a repository artifact bound to a concrete revision and checked by deterministic systems before anyone considers release.

Operating model

Authority must be named.

  • Policies belong at durable scopes.
  • Owners define stop authority.
  • Budgets need accountable limits.

The operating model chapter names who may grant access, which checks are required, where runners may execute, how deployment identity is issued, how attempts and spend are bounded, and who may stop or escalate the loop.

The sandbox profile and future enterprise profile share the same learner-facing concepts. The difference is policy scope, identity, ownership, and provisioning maturity, not duplicated workshop content or hidden enterprise assumptions.

Open Lab 3

Migration is a controlled wave.

  • Keep stable systems stable.
  • Move evidence-producing paths first.
  • Rebuild deployment identity deliberately.

A realistic migration does not move every board, feed, repository, pipeline, and secret at once. Start with repositories where acceptance is clear, tests are fast, data is synthetic or low risk, and rollback is simple.

Convert pipelines deliberately, review the converted workflows by hand, keep existing work item or package systems where they reduce risk, and re-establish deployment with OpenID Connect rather than copying long-lived secrets.

Trusted delivery

Checks must be safe before code arrives.

  • Use least-privilege tokens.
  • Pin third-party actions immutably.
  • Treat pull-request text as data.

Trusted delivery starts before an agent-generated pull request exists. Workflows that run on untrusted pull requests need read-only permissions, immutable action references, bounded time, explicit concurrency, and no protected secrets.

The lab uses a safe synthetic injection exercise, native GitHub security evidence, and revision mapping to show what deterministic systems can prove. Recorded artifacts cover entitlement-dependent or slow views without pretending that a simulation is a live control.

Open Lab 4

Release authority stays human.

  • Checks can block merge.
  • Approvals gate environments.
  • Outcomes are observed after deployment.

A green build, passing tests, CodeQL status, dependency review, and required approval can make a change ready for a human release decision. They do not prove that the new bytes are already deployed, healthy, or producing the intended business outcome.

Post-deployment evidence answers a different question: what ran, from which revision, through which workflow identity, under which environment approval, and what health or telemetry was observed after release. Keep those records distinct.

For the deeper demonstration path, open the trusted delivery guide.

Capstone

Evidence must name one revision.

  • Missing artifacts block release.
  • Wrong-revision artifacts also block.
  • Simulations stay labelled.

The capstone asks you to decide, not just inspect. You read intent, proposal, checks, review, deployment record, and follow-up state. Then you decide whether the packet is ready for a human release decision, blocked, waiting for a named owner, or escalated.

Missing release evidence blocks. A green deployment record for a different commit also blocks. The lesson is not that every checklist cell can be made green; the lesson is that evidence only counts when it is complete, attributable, and tied to the exact revision under review.

Open Lab 5

The next action must be earned.

  • Accepted state can justify no-op.
  • Waiting names a human owner.
  • Exhausted repair escalates cleanly.

A loop that cannot read its previous accepted outcome will either repeat work, spend attempts on waiting states, or hide escalation behind silence. The capstone turns those failure modes into explicit decisions.

A justified no-op is a valid outcome when the same accepted work is observed again. Waiting consumes no model attempt while a named human owns the decision. A trusted failure may authorize one bounded repair; an exhausted repair escalates without starting another worker.

Recovery and cleanup

Recover without bypassing evidence.

  • Use each lab's reference artifact.
  • Declare recorded evidence as recorded.
  • Escalate corrupt state, not hide it.

Each lab guide names its recovery path. If you run out of time, copy the lab's reference artifact, continue from the next checkpoint, and say clearly which part you completed and which part came from a prepared reference.

If a preview capability, security entitlement, or environment view is unavailable, use the recorded artifact named by the lab. Treat it as evidence from a recording, not as a fresh result from your station repository.

Rule

Never reset or rewrite state to regain authority. If a repository rule, review requirement, attempt limit, or evidence check blocks you unexpectedly, preserve the observable message and ask the instructor to diagnose the control.

Leave durable artifacts behind.

  • Do not delete the station repository.
  • Close local services you started.
  • Keep issues and pull requests reviewable.

At the end of the day, leave your station repository intact unless the instructor gives explicit cleanup instructions for the classroom environment. Pull requests, checks, rejected pushes, issues, and reviews are the artifacts you may want to revisit.

If you used a local clone or started a local service, stop the service, close terminals that hold credentials, and delete only local scratch copies you created yourself. Do not delete shared classroom repositories, evidence issues, or pull requests.

Adoption roadmap

Start where outcomes are verifiable.

  • Choose frequent reversible work.
  • Measure accepted outcomes.
  • Expand after controls hold.

Good pilots have clear acceptance criteria, fast deterministic checks, low data sensitivity, active owners, and a reversible deployment path. Defer identity, payment, regulated clinical logic, and production-infrastructure repositories until governance and review capacity are proven.

Measure accepted outcomes, human attention needed, duplicate suppression, failed attempts, time to evidence, and bounded spend. Generated lines and token counts do not tell you whether the loop improved engineering quality.

Adopt the loop, not a demo.

  • Intent lives in GitHub.
  • Evidence gates material changes.
  • People own release decisions.

Leave with one candidate repository, one deterministic check set, one accountable owner for review and release, one allowed agentic workflow, one budget boundary, and one explicit stop path.

If those pieces are not named, automation will fill the gap with chat history, defaults, and optimism. If they are named, GitHub can orchestrate people, agents, checks, security signals, and deployment records in one durable loop.

Agents propose, deterministic systems provide evidence, and accountable people retain authority over material changes and production release.
