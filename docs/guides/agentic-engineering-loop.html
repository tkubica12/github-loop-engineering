Lifecycle and continuation

Read back before acting again.

  • Carry stable work identity into intake.
  • Verify externally and persist the receipt.
  • Keep human authority outside the worker.

The familiar intent, proposal, proof, approval, release and improvement flow remains the inner governed change. Human product, review and release authority remain outside the worker.

Run the continuation live.

  • The verifier builds disposable source copies.
  • The regression must catch both mutations.
  • A live run is not prerecorded evidence.

Source

Live local continuation: the public repository no longer retains a source-bound recorded receipt. Run the trusted verifier during rehearsal or presentation and read the result it prints. The run verifies the original suite, the proposed malformed-percent regression, and wrong-status plus wrong-body mutation probes in disposable local copies. This remains local deterministic verification, not GitHub Actions, a pull request, review, merge, release, or deployment.

node teacher\demos\security-remediation\scripts\verify-continuation.mjs

Expect VERIFIED local maintenance verification followed by four passed checks. The verifier refuses to overwrite a report unless you supply a new path with --report. Read the result literally: it is a live local verification of the prepared continuation test, not retained evidence and not a remote platform event.

Participants and control contract

Distinct roles create accountable decisions.

  • Product owners define intent.
  • Agents propose and challenge; Actions produces evidence.
  • Code owners accept or reject material risk.

Product owner

Defines outcome, acceptance, constraints, and risk in a durable issue.

Coding agent

Researches, plans, changes code, runs tests, and proposes a pull request. GitHub Copilot fills this role here; an external local harness such as OpenCode can take a bounded piece of the same work.

Review agent

Challenges the proposal against repository context and specialist concerns.

GitHub Actions

Produces deterministic build, test, security, and provenance evidence.

Code owner

Accepts or rejects material risk with attributable authority.

Agentic Workflow

Finds evidence-backed follow-up work within declared safe outputs.

Every control answers a specific question.

  • Trace intent, work, checks, and risk acceptance.
  • Identify exactly what reached the environment.
  • Persist prior state and the next owned decision.

QuestionGitHub artifact or control
Why are we changing this?Issue, specification, project context
Who or what did the work?Agent session, branch, commits, pull request provenance
Does it behave correctly?Required tests and checks
Is it secure and maintainable?Code scanning, secret scanning, dependency signals, code quality, review
Who accepted the risk?CODEOWNERS, required review, ruleset result
What reached the environment?Artifact attestation and deployment record
What prior state did this run consume?Stable work identity, retained recommendation and trusted receipt
What happens next?Report, evidence-authorized retry, waiting-human, escalation, no-op or verified exit

Adoption

Start bounded.
Measure accepted outcomes.

  • Choose tested, owned, reversible repositories.
  • Govern access, evidence, release, and budget.
  • Reject hidden autonomy and generated-line success metrics.

Start

Choose tested, owned, reversible repositories with clear backlog and low blast radius.

Govern

Govern access, tools, runners, network, token permissions, required evidence, merge, deployment, budget.

Measure

Measure accepted verified outcomes, human attention, failures, duplicates, cost per accepted outcome, and developer experience.

Avoid

Avoid generated-line metrics, universal rollout, shared long-lived secrets, hidden agent autonomy, and unreviewed production changes.
