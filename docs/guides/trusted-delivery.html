Verification evidence

Four decisions need distinct evidence.

  • Verification is not artifact creation.
  • Operator intent is not independent approval.
  • Deployment identity is not application correctness.

Trace a reviewed commit through four distinct decisions: deterministic verification, artifact creation, operator release intent, and Azure deployment identity. The service uses only synthetic stock identifiers and deploys only to a disposable test target.

Warning

Sandbox limitation: required environment reviewers are unavailable for a private personal repository on GitHub Free, Pro, or Team. The entered SHA is operator intent, not independent approval. No production deployment is represented.

A specific failure can authorize repair.

  • Require successful setup first.
  • Match the failed command and assertion.
  • Bind green evidence to the corrected SHA.

  1. Open the prepared pull request and select Checks.
  2. Open the failed Deterministic CI run. Verify that the zero-quantity boundary test failed against the displayed head SHA.
  3. After the focused correction arrives, refresh the same pull request. Verify that a new SHA has a green run.
  4. Download deterministic-evidence-<sha>. Open manifest.json and match its commit to the green run.

Checkpoint: you can point to the proposal SHA, test result, and artifact manifest without relying on a presenter statement or agent summary.

Warning

Only a specific task failure can authorize repair: first require every setup step to succeed. Then require the failed step to have run exactly npm test -- --test-reporter=tap and the original quantity assertion to report expected HTTP 400 but actual HTTP 201. An arbitrary failed workflow, runner error, install failure, or different assertion is blocked or unclassified evidence—not permission for an agent to edit code.

Release authority

Packaging does not authorize deployment.

  • Select an exact main-branch SHA.
  • Package and retest that revision.
  • Only deployment receives OIDC permission.

  1. Open .github/workflows/release.yml.
  2. Find the gate that requires a full lowercase SHA, requires dispatch from main, and compares the input with GITHUB_SHA.
  3. Find the package job. Confirm it checks out that exact SHA, reruns tests, writes a release manifest, and uploads release-<sha>.
  4. Compare permissions. The gate and package receive contents: read. Only deploy-test receives id-token: write.
  5. Open the Azure login step. Confirm the client, tenant, subscription, and app name are identifiers in repository variables, not a stored client secret.
  6. Open the completed release run only if the presenter has verified it live. Match its release SHA to main, then open the synthetic /health response.

Checkpoint: packaging and deployment are separate jobs; the Azure trust subject contains immutable owner and repository IDs plus ref:refs/heads/main; the deployment identity is scoped to one web app. The sandbox does not require a GitHub Environment.

The input makes the operator choose and record the exact commit. It prevents an ambiguous “deploy latest” action. The same operator can still merge and dispatch in this sandbox, so this does not prove separation of duties. A supported enterprise profile can add real required reviewers and organization policy without changing the workflow’s evidence model.

Build, test, packaging, identity, and deployment are deterministic controls. Agent recommendations may help diagnose a failure, but they do not belong inside the release authority path and no agent credits are needed for this exercise.

Assign each control one job.

  • Tests establish behavior for one commit.
  • Manifests identify packaged bytes.
  • Identity and approval remain separate controls.

For an enterprise station, keep the same repository concepts and configure the owner, repository, region, subscription, and web app at runtime. Add organization rulesets and genuine environment reviewers only after a capability check. Do not turn a local screenshot or presenter click into a claimed policy control.

Recovery and sources

Recover without weakening the boundary.

  • Resume the same run and evidence chain.
  • Do not introduce billable capacity or persistent secrets.
  • Label recorded and local results honestly.

Match the symptom to the action

CI is queued

Inspect the workflow and run local verification. Label that evidence local, then resume on the same GitHub run.

F1 is unavailable

Stop before Azure creation. Do not switch to a billable SKU during the session. Complete the package path and state that no deployment occurred.

OIDC fails

Compare the exact subject printed by setup: repo:OWNER@OWNER_ID/REPO@REPO_ID:ref:refs/heads/main. A repository created after 15 July 2026 must not use the legacy name-only subject. Keep the scoped role; never substitute a long-lived secret as a live fix.

No live evidence is available

Use the local fixture and workflow source. State that this is a fallback walkthrough, not a live GitHub or Azure result.

To resume, reopen the existing pull request or workflow run. To reset or remove the isolated resources, follow the scoped operator commands.
