Lifecycle and evidence

Return to checked state.
Not a blank prompt.

  • Scheduling creates intake, not continuity.
  • External verification produces evidence.
  • Read prior state before authorizing another action.

The decision can authorize one evidence-informed retry, wait for or escalate to an owner, record a justified no-op, report a result, or exit verified. Scheduling only creates intake. A later run becomes continuous when it reads prior state and changes its decision accordingly.

Rule

Inner change story: Intent, Propose, Prove, Approve, Release, and Improve still explain one governed software change. Release remains separately authorized; not every maintenance loop releases software.

A verdict limits the claim.

  • Historical GitHub lineage remains historical.
  • Local continuation proves only its stated scope.
  • Controller fixtures do not prove agent execution.

Verdict, evidence meaning, and permitted claim

VERIFIED_LOCAL

Evidence meaning: A coordinator-observed local agent invocation is bound to trusted external verification.

Permitted claim: Local agent continuation for that new collection only; not GitHub execution, approval, merge, deployment, or signed provider telemetry.

CONTROLLER_PROOF_ONLY

Evidence meaning: A deterministic fixture exercised controller transitions without an agent.

Permitted claim: Controller behavior only.

BLOCKED

Evidence meaning: Required source, scope, identity, chronology, or verification evidence is absent or invalid.

Permitted claim: No completed continuation.

NOT_EXECUTED

Evidence meaning: No continuation report was supplied.

Permitted claim: No continuation claim.

Evidence class, recorded facts, and boundary

Historical GitHub lineage

What it records here: Issue, reviewed change, checks, approval, release, and retained maintenance recommendation.

Boundary: Recorded platform history; it is not upgraded by later local work.

Local Copilot continuation

What it records here: A 15 September 2026 task consumed retained state, proposed one test, passed trusted checks, and replayed to no-op.

Boundary: Coordinator-attested local execution; no remote write or live collector claim.

Simulation

What it records here: Capstone fixtures exercise report, retry, wait, block, escalate, and no-op decisions.

Boundary: Deterministic teaching evidence; no model or learner pull-request evidence.

Layers and contract

A prompt cannot enforce a loop.

  • Context provides facts, not a ledger.
  • Harness permissions constrain execution.
  • Loop policy controls recurrence.

Prompt

Prompt instructs one action

It states the immediate objective and requested output. It does not provide durable state or enforce policy.

Context

Context supplies relevant facts

Issues, code, architecture decisions and repository conventions guide the work. AGENTS.md is durable convention, not a run ledger.

Harness

Harness executes within a boundary

GitHub Copilot is the primary worker. Each optional harness retains its own tools, permissions, credentials, network and isolation properties.

Loop policy

Loop policy controls recurrence

The contract, controller, verifier, persistence adapter and human owners determine whether work continues or stops.

A worktree isolates edits from another checkout. It is not an operating-system security sandbox. A per-run output cap limits one operation; stable identity and reconciliation prevent duplicate work across runs.

Keep four records separate.

  • Contract defines authority; context informs an attempt.
  • State survives the next process.
  • Evidence binds checks to the revision.

Warning

No-op requires evidence. Inaccessible, stale, malformed or wrong-identity evidence is blocked or unknown. It is never healthy and never a no-op.

A contract exposes the control system.

  • Name identity, scope, owner, and verifier.
  • Persist finite limits across attempts.
  • Parsing policy does not grant or enforce every permission.

  1. Name a stable loop and work identity: profile, station, repository, objective and contract version.
  2. Declare the exact eligible trigger and intake. Separate task identity from changing observations.
  3. Limit reads, writes and actions. Forbid approval, merge, deployment, policy changes, credentials and trusted-verifier edits.
  4. Name the worker, deterministic verifier, product owner and release owner.
  5. Define durable state, update rules, retention and interrupted-publication reconciliation.
  6. Set explicit component limits. This teaching controller allows two agent attempts total: the initial attempt and one repair authorized by specific verifier evidence.
  7. Define success, report, no-op, waiting-human, blocked, escalated and stopped outcomes.

The schema validates structure. Tools, tokens, validators, state transitions and human controls enforce behavior. General controller and lab callers may supply explicit input.limits with maxAttempts and deadlineHours; otherwise they default to two attempts and 24 hours. Live continuation is demonstrated by running the security-remediation verifier and reading its result, not by replaying a stored receipt. Legacy version-one records without policy fields retain their original fixed 2/24 interpretation and digest. The rest of the compact contract—scope, roles, timeouts and permissions—is descriptive or enforced separately by adapters, platform controls and people; parsing it does not grant or automatically enforce those fields. Worker time, detector time, inference credits and presenter wait cutoff remain separate limits.

Decisions and pilot selection

Every next decision needs evidence and ownership.

  • Specific trusted failure can authorize one repair.
  • Wait, no-op, block, and escalation start no worker.
  • Verified work still needs separate human authority.

Choose recurring, verifiable, reversible work.

  • Stable intake needs an accountable owner.
  • External checks judge the outcome.
  • Measure accepted outcomes, attention, duplicates, and cost.

Measure accepted verified outcomes, human attention, failed or blocked exits, duplicate work and cost per accepted outcome. The synthetic telemetry in this workshop is a fixed fixture whose arithmetic and identity are checked; it is not measured business improvement.

Operation and authority

The CLI proves decisions.
Not agent execution.

  • Use the prepared input and owned state directory.
  • Missing scope evidence blocks acceptance.
  • Reconcile locks; never break them automatically.

Run the controller only with an input file supplied by the lab or operator flow. The file carries the exact identity, event and trusted fixture receipt. Keep state in an explicitly owned directory under .workshop.

node platform/scripts/loop.mjs step OWNED_STATE_DIRECTORY INPUT_JSON
node platform/scripts/loop.mjs reset OWNED_STATE_DIRECTORY INPUT_JSON

step accepts the prepared intake, verify, waiting-human, stop, or publication event and returns the state, decision, reason, dispatch flag, prior digest and new state digest. A trusted task receipt must explicitly carry scopeValid: true; false or missing scope evidence blocks acceptance. State is stored as <workId>.json and replaced atomically. An exclusive per-work lock is never broken automatically; an existing lock means the operator must reconcile an active or interrupted invocation.

reset removes only the state matching the input identity. These commands spend no inference and create no GitHub issue, pull request, review, workflow run, deployment or cloud resource. A deterministic replay proves controller transitions only.

Warning

Do not invent input JSON. Use the exact prepared fixture and path named by the lab. Optional live station commands require a configured repository and ref, capability checks, and matching published workflow source and lock; they are not part of this account-free core.

Share semantics.
Keep authority explicit.

  • Local JSON and review fixtures are simulations.
  • Enterprise controls require effective-policy checks.
  • People retain product, review, and release decisions.

Sandbox

Sandbox keeps the core account-free

Owned local JSON models persistence and human-decision fixtures model review. They are simulations, not live GitHub controls or security isolation.

Enterprise

Enterprise adds capability-gated controls

A configured organization can add rulesets, teams, licensed security, governed runners, budgets and Azure OIDC release approval after effective-policy checks.

Authority

Authority stays explicit

Copilot performs bounded work. GitHub stores governance and evidence. Azure OIDC supplies release identity. People retain product, review and release decisions.

OpenCode remains an optional experimental external harness. Shared artifacts do not imply equal permissions, security properties, model quality or benchmark equivalence.

Name the stop path precisely.

  • No-op means checked state, not missing evidence.
  • Waiting and escalation retain a named owner.
  • Verified exit does not erase separate approval.

Work identity
The stable key that says which objective this state belongs to; a workflow-only revision does not create a new application task.
Observation
A revision, evidence fingerprint or current fact recorded against stable work.
No-op
A justified decision that checked state is already accepted or not actionable.
Blocked
The controller cannot safely decide because required identity, access or evidence is invalid or unavailable.
Waiting-human
A named person owns the next product, review or release decision; the model is not invoked repeatedly.
Escalated
The attempt allowance or deadline is exhausted and a named owner must decide.
Verified exit
The required external check passed and the result is persisted; any separate human approval remains separate.

A useful loop earns each next action from checked evidence, persisted state, explicit limits, and accountable ownership.
