Before you start

Do real work on GitHub.

  • Repair one pull-request workflow.
  • Prove hostile input stays data.
  • Read native security evidence.

Outcome: a reviewed pull request that adds a hardened title-check workflow, a second proof pull request whose title contains a safe shell payload, a completed CodeQL run, and a written release-boundary statement.

You need

Your station repository
Use the repository URL from your preparation message. You have write access and can create branches, pull requests and workflow files.
GitHub Actions
The repository already contains the deterministic CI workflow at .github/workflows/ci.yml. The workflow uses read-only permissions, timeout, concurrency and commit-pinned actions.
A review partner
Ask someone at your table to review the hardened workflow before you merge it. If you are alone, read the review checklist out loud before merging.

Warning

Real repository boundary: do not paste credentials, customer data or active tokens anywhere in the station repository. The only payload in this lab is a harmless pull-request title used to prove shell metacharacters stay text.

Starting state

Your station repository is the system of record. The local files in this lab are only reference material:

  • Unsafe fragment — read only; never execute it.
  • Starter workflow — the deliberately vulnerable shape.
  • Reference workflow — the hardened target.

Checkpoint: you can name the repository, the default branch and the person who will review your first pull request.

Harden the workflow

Read the flaw.
Never run it.

  • Pull-request titles are untrusted.
  • Expressions generate a shell script.
  • Read-only tokens still deserve care.

Open artifacts/unsafe-fragment.yml and artifacts/title-check.starter.yml. Read the final step:

run: echo "${{ github.event.pull_request.title }}"

Warning

Never execute the unsafe fragment. A pull request title is attacker-controlled text. GitHub interpolates the expression before the runner creates the shell script, so a crafted title can become shell syntax in the run: block.

The example still uses permissions: contents: read. That reduces blast radius, but it does not make shell injection acceptable. The correct repair is to pass the title as data, quote the expansion, keep permissions read-only, and avoid unpinned actions.

Checkpoint: explain why $(printf SAFE_PAYLOAD) in a title would execute inside the unsafe double-quoted echo, but should print literally after the repair.

Repair on a branch.

  • Bind the title to env.
  • Quote the shell expansion.
  • Preserve read-only execution.

  1. Open your station repository on GitHub.
  2. Create a branch named lab-04-harden-title-check.
  3. Create .github/workflows/title-check.yml on that branch.
  4. Start from the starter workflow, then apply the repair below.
name: Pull request title check

on:
  pull_request:

permissions:
  contents: read

jobs:
  title:
    runs-on: ubuntu-latest
    steps:
      - name: Inspect title
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
        run: printf '%s\n' "$PR_TITLE"

This workflow needs no checkout action. If you add any action in your own experiment, pin it to a full commit SHA. Compare the existing .github/workflows/ci.yml to see that pattern in the station repository.

Commit the file, open a pull request into the default branch, and title it Lab 4 harden title check. Wait for the existing CI workflow to pass.

Review checklist

  • permissions remains contents: read.
  • The title is assigned to PR_TITLE in env.
  • The shell reads "$PR_TITLE", not the GitHub expression.
  • No action uses a version tag such as @v4.

Ask for review. Merge only after the reviewer can explain why the title is now data rather than shell source.

Prove and scan

Make the payload visible.

  • Open a second pull request.
  • Put metacharacters in the title.
  • Read the workflow log.

After the hardened workflow is merged, create another branch named lab-04-title-payload-proof. Make a harmless documentation change, such as creating docs/lab-04-title-proof.md with one sentence about the lab.

Open a pull request with this exact title:

Lab 4 proof $(printf SAFE_PAYLOAD)

Open the Pull request title check run and expand Inspect title. The log should print the exact title, including the literal characters $(printf SAFE_PAYLOAD). It must not print only SAFE_PAYLOAD as the result of command substitution.

Rule

Do not make the payload destructive. You only need shell metacharacters that would be meaningful to an unsafe shell script. The proof is that the hardened workflow preserves them as text.

Checkpoint: leave the proof pull request open until your table partner has seen the log. Then close it without merging, or merge it only if your facilitator wants the note retained.

Add native code scanning.

  • Commit CodeQL as reviewed code.
  • Run it on main.
  • Read the Security tab alert.

Create a branch named lab-04-enable-codeql. Add .github/workflows/codeql.yml with this workflow, modeled on the prepared security demonstration:

name: CodeQL

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: codeql-${{ github.ref }}
  cancel-in-progress: true

jobs:
  analyze:
    name: CodeQL
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      contents: read
      actions: read
      security-events: write
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
        with:
          persist-credentials: false
      - uses: github/codeql-action/init@cdf488f595d80d6e07e03d4674febd5ab45fa938
        with:
          languages: javascript-typescript
          build-mode: none
          queries: security-extended
      - uses: github/codeql-action/analyze@cdf488f595d80d6e07e03d4674febd5ab45fa938
        with:
          category: javascript-security
  1. Open a pull request, confirm CI is green, request review, and merge.
  2. Open Actions, choose CodeQL, then run it on the default branch.
  3. Open Security, then Code scanning. Open the alert created by the scan.

In a seeded station, expect a JavaScript finding such as caller-controlled path access in the synthetic export path. Read the rule, file, line and data flow. If your repository produces no alert or CodeQL is unavailable, use the recorded security-remediation evidence and say clearly that you are reading archived evidence, not your station scan.

Checkpoint: write one sentence naming the CodeQL rule and one sentence stating what a clean scan would not prove.

Connect delivery to release

Secret Protection stops earlier.

  • Do not push token-like strings.
  • Observe the native rejection.
  • Rotate real exposed credentials.

Open the Secret Protection reference: recorded native response and clean control evidence. Read the blocked REST Create a blob response, the token type, the accepted clean blob, and the unchanged branch SHA.

Warning

Do not test this by committing a credential-like string. Repository push protection, custom patterns and delegated bypass depend on organization configuration. A shared workshop repository is not the place to discover whether a realistic secret creates an alert.

If your facilitator demonstrates the live control, they use the supported inactive learning sample described in the reference. Treat that as a GitHub-native rejection before history, not as proof that every possible secret will be detected.

Checkpoint: contrast CodeQL with Secret Protection. CodeQL inspects committed application code; push protection rejects supported secret patterns before a commit or ref update.

Checks inform.
People authorize.

  • Head is the reviewed proposal.
  • Merge is main-branch code.
  • Release packages exact bytes.

Open the full-day delivery section on release evidence: Trusted delivery. Then write a three-line release statement for your station repository:

Reviewed head revision
The commit reviewed in the pull request. Green checks here prove only that proposal's evidence.
Merge revision
The commit on the default branch after merge. A release should package this exact revision, not a convenient checkout.
Released bytes
The artifact or deployment manifest that names the packaged revision and the workflow run that produced it.

A green CI check, a CodeQL result, a Secret Protection rejection, or an agent recommendation never grants release authority. They inform the decision. A named person or governed environment approves release.

Checkpoint: state who may approve a pharmacy release in your team model, and which deterministic checks must be green before that person can approve.

Recovery and extensions

Recover without weakening controls.

  • Use the reference workflow.
  • Check whether the workflow merged.
  • Label recorded evidence honestly.

The title workflow is red
Compare your file with the reference workflow. The usual errors are reading the GitHub expression inside run, missing env, or forgetting quotes around "$PR_TITLE".
The proof pull request does not run the title check
Confirm the hardening pull request was merged first. Pull-request workflows are evaluated from the default branch for this proof path.
CodeQL cannot upload results
Check that the job-level permissions include security-events: write. If the repository or license does not allow code scanning, use the recorded evidence and label it honestly.
Security tab shows no alert
Open the CodeQL run logs and verify extraction completed. A zero-alert scan is still evidence, but it is not the path-injection finding. Use the recorded finding for the security discussion.
You need to reset
Close the proof pull request, delete lab branches, and leave the merged hardening and CodeQL workflow only if your facilitator wants the station to retain them.

Extend after the proof.

  • Add branch protection intentionally.
  • Require the right checks.
  • Design artifact provenance.

Require the hardened checks
Add branch protection or a ruleset that requires deterministic CI and CodeQL before merge. State whether your station profile allows you to enforce it yourself or only observe the setting.
Break the workflow safely
On a temporary branch, change "$PR_TITLE" back to the expression-bearing run line. Do not merge it. Confirm review would reject it.
Design provenance
Sketch an artifact manifest that records source commit, workflow SHA, run ID, test result and approving environment. Mark which fields are integrity evidence and which would require signed attestation.

Trusted delivery is an evidence chain: untrusted input stays data, native scanners report what they observed, and release remains a human or governed-environment decision.
