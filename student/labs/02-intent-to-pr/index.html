Before you start

The handoff is the product.

  • A person confirms the need.
  • Tests make acceptance deterministic.
  • Review judges the agent proposal.

Outcome: a merged pull request in your station repository that implements the reservation requirement you refine from the intake context, with GitHub Actions green and a human review confirming the scope.

The merged revision becomes the verified handoff that Chapter 5 consumes. Do not rely on chat history, local notes, or an agent summary as the system of record.

You need

Your station repository
Use the repository URL assigned for your station. You have write access, and the repository already contains the pharmacy service, workflows, the synthetic intake context in context/intake/, and seeded backlog issues.
A signed-in Copilot surface and a station clone
Step 1 runs the coaching agent in an interactive Copilot surface that reads repository custom agents: Copilot CLI or Copilot Chat in VS Code, opened in a clone of your station on the default branch. Prepare it before the lab starts; Step 1 has no time for installation or sign-in. Without one, pair with a partner and use the question list instead.
Your team GitHub Project board
Use the project linked from the station instructions. It is where the issue stays visible after delegation starts.
A browser
The core path uses GitHub Issues, Projects, the web editor, Actions, and pull request review. PowerShell commands are optional.
Optional Copilot coding agent entitlement
GitHub Copilot coding agent requires the right plan, policy, and repository enablement. If it is unavailable, use the manual fallback in this guide.

Refine the intent

Signals are not requirements.

  • Evidence overlaps, conflicts and distracts.
  • The coach asks; you decide.
  • Nothing is drafted before you confirm.

Your station repository contains synthetic organizational signals as an organizational search tool would return them: a store chat thread, a support ticket digest, and a product owner email. They point to one real need, surrounded by noise. Find the need yourself; the coach only asks questions.

  1. In your station repository on GitHub, open context/intake/. Read README.md, then skim chat-thread.md, ticket-digest.md, and stakeholder-email.md. Spend no more than two minutes.
  2. Open the Issues tab and scan the issues labeled backlog. They are already planned work.
  3. Open your station clone on the default branch. If you have no clone yet, run gh repo clone OWNER/REPOSITORY with your station repository, then enter the new folder. Run git switch main and git pull so the agent file is present.
  4. Start an interactive Copilot surface that reads repository custom agents:
    • Copilot CLI: run copilot in the clone, enter /agent, and choose requirement-refiner.
    • VS Code: open the clone, open Copilot Chat, and choose requirement-refiner from the agents dropdown.
  5. Send your first reading of the evidence in one sentence: 
    Coach me. I think the evidence points to: <your one sentence>
  6. Answer the coach's questions in your own words. When it asks whether something is already planned, check the Issues tab and tell it what you found.
  7. When your need statement is specific enough to test, send it after the confirmation keyword: 
    CONFIRMED: <your final need statement>
  8. Copy the draft the coach returns into a scratch note outside the repository. Do not create the issue yet.

Expected result

The coach asks one or two questions at a time, reflects your wording back, and refuses to state the requirement for you. It produces a draft in the order of the Reservation capability form only after your CONFIRMED: message, and marks anything you did not confirm as NOT CONFIRMED. It creates no issue, file, or branch.

Do not delegate this step

Do not assign the coach to an issue or choose it for a Copilot cloud agent task. That runs in the background and opens a pull request, which is the wrong shape for a conversation. disable-model-invocation only stops Copilot from choosing the coach automatically; running it interactively is your choice.

Fallback — no interactive Copilot surface

Pair with a table partner. Your partner reads the evidence and asks you the questions below, one at a time, without offering answers. Write the draft yourself in the form order, then label it Coached by partner in Step 2. This is a supported human substitute, not a simulation of the agent.

  • Which sources support your reading, and which contradict it?
  • Who experiences the problem, and what do they observe today?
  • What would that person see when it is solved?
  • Which requests are already planned, unrelated, or untrusted?
  • Where do sources disagree, and who decides?
  • What must stay unchanged for existing clients?
  • How would a deterministic test prove each statement?

Checkpoint: you have a draft whose need statement you confirmed yourself, and a short list of what you set aside as noise.

Tools enforce; prompts only ask.

  • Minimal tools bound the coach.
  • A human gate precedes drafting.
  • Instructions layer by scope.

A custom agent is a Markdown file in .github/agents/. YAML frontmatter configures it; the Markdown body, up to 30,000 characters, is its prompt. Open .github/agents/requirement-refiner.agent.md in your station repository.

---
name: requirement-refiner
description: Coaches a person to refine one testable requirement ...
tools: ["read", "search"]
disable-model-invocation: true
---
description
The only required property. Copilot uses it to explain and select the agent.
tools
The enforcement boundary. read and search let the coach inspect evidence and code; it has no tool to edit files, run commands, or write issues. Omitting tools grants every available tool, including configured MCP servers, so a coach without a list could open issues itself.
disable-model-invocation
Copilot cloud agent does not pick this agent automatically; a person must choose it.
Prompt body
Coaching rules and the CONFIRMED: gate. The body is guidance the model follows, not a control. The tool list and your manual issue creation are what make the gate hold.

Why a minimal tool list

Every tool is an action the agent can take on untrusted input. The ticket digest contains an instruction addressed to an assistant; a read-only coach can report it but cannot act on it. Unrecognized tool names are ignored rather than rejected, so review the list you ship instead of assuming a typo fails loudly.

Why a human confirmation gate

Refinement decides product scope. Only a person with the product owner's authority can confirm it. The coach waits for your explicit keyword, drafts only what you confirmed, and leaves the issue to you. GitHub then records the decision as an issue you authored and a comment that explains the differences.

How instructions layer

.github/copilot-instructions.md
Repository-wide rules for every Copilot request.
.github/instructions/*.instructions.md
Path-scoped rules. The applyTo glob in each file's frontmatter selects what it governs: src/**/*.mjs, test/**/*.mjs, and context/** in your station. They combine with the repository-wide file when Copilot works on matching paths.
AGENTS.md
The same contract for external harnesses and Copilot surfaces that read it.
.github/agents/*.agent.md
A named role with its own prompt and tools, used only when selected or inferred.

CODEOWNERS assigns /.github/ and /context/ to the platform owner, so changes to the coach, instructions, or evidence need that review.

Availability

Validated against GitHub documentation on 2026-09-22. Custom agents work in Copilot cloud agent on GitHub.com, Copilot CLI, and supported IDEs; support is in public preview for some IDEs, and properties such as model and mcp-servers apply only in some surfaces. Check the surface you use.

Create the handoff issue

Write the issue as a contract.

  • Compare your draft with the contract.
  • Acceptance stays observable.
  • Record what you missed.

The product owner has now confirmed the final wording in feature-request.md. It is the contract the rest of the lab tests. Your draft is not discarded: the differences are the learning.

  1. Open feature-request.md next to your draft and note what matches, what you missed, and what you would have added.
  2. In your station repository, choose Issues, then New issue, and select Reservation capability.
  3. Copy the title, outcome, acceptance criteria, constraints, and risk from feature-request.md, not from your draft.
  4. Add links to the workshop copies of specification.md, decision-record.md, and suggestion.test.mjs. These files are not in your station; copy each link address from this guide.
  5. Create the issue. Keep your draft; you record the comparison in Step 5, after delegation starts.

Use this title exactly so your table can find the same work:

[Reservation] Suggest an available substitute when stock is zero

Expected result

The issue states that POST /reservations still returns 409 for unavailable stock, adds one deterministic suggestion when eligible, omits it when no candidate qualifies, and never changes stock while suggesting.

The constraints must say that the implementation is dependency-free, synthetic-data only, and bounded to src/inventory.mjs plus the optional new test/suggestion.test.mjs.

Why this matters

An agent must not infer product policy. Outcome, acceptance, constraints, and risk belong in the issue before anyone starts implementation, and the person with authority confirms them.

Put intent where the team works.

  • The project board shows ownership.
  • Status survives agent handoff.

  1. Open the issue sidebar.
  2. Find Projects.
  3. Add the issue to your team Project board.
  4. Set the status to the intake column used by your station.

If the project field is hidden, use the repository or organization project search from the issue sidebar. Ask your table partner to confirm the card appears on the shared board. If your station has no Project board, skip this step and tell the facilitator; the issue and pull request still carry the handoff.

Checkpoint: the issue is on the board, when your station has one, before you add code. Otherwise the issue itself is the visible record. Delegation starts from visible team intent, not a private branch.

Commit expected red

Prove the gap before fixing it.

  • Create a test branch.
  • Commit expected red.
  • Keep the default branch clean.

  1. In your station repository, create a branch named lab-02-substitute-suggestion.
  2. On that branch, create test/suggestion.test.mjs.
  3. Copy the full contents of artifacts/suggestion.test.mjs into the new file.
  4. Commit the file with Add substitute suggestion acceptance test.
  5. Open a draft pull request from the branch into the default branch.

Expected red

GitHub Actions should run against the draft pull request and show a failing test, because src/inventory.mjs does not yet return a suggestion.

Open the failed check and confirm the failure is about the missing suggestion contract, not syntax, import paths, or unrelated tests.

If Actions is not red

Confirm the file path is exactly test/suggestion.test.mjs, the branch is not the default branch, and the committed file matches the artifact. Fix the test branch before delegating implementation.

Checkpoint: the draft pull request is committed and expected-red. This is visible evidence that the acceptance test detects the current gap.

Delegate and review

Delegate the smallest safe change.

  • Use the issue as context.
  • Bound application edits tightly.
  • Fallback stays honest.

Preferred path — Copilot coding agent

  1. Open the structured issue.
  2. Use the repository control for delegating the issue to GitHub Copilot coding agent.
  3. Paste the bounded prompt below.
  4. While Copilot works, add a comment to the issue: paste refinement-comparison.md and fill in one line per heading. Start the comment with Retrospective, not scope.
  5. Wait for Copilot to open or update a pull request. Copilot often needs more than five minutes; open Step 6 and read the review questions while you wait.

Post the comparison only after delegation starts. Copilot reads the issue when you assign it, and your draft or the noise you set aside must not become implementation context.

Implement the reservation substitute suggestion from this issue.
Use the committed red acceptance test as the proof.
Change only src/inventory.mjs.
Do not edit workflows, package files, ownership, server code, or existing tests.
Keep the service dependency-free and use synthetic data only.
Return one suggestion with sku, name, and available for the first same-category candidate with enough stock, ordered by SKU.
Omit suggestion when no candidate qualifies.
Do not mutate stock when returning a suggestion.
Run npm test and iterate until GitHub Actions is green.

If Copilot opens a separate pull request that does not include the committed acceptance test, do not merge it as-is. Bring the src/inventory.mjs change into your expected-red pull request, or add the committed test to Copilot's pull request, so Actions proves both files together.

Fallback path — no Copilot coding agent entitlement

If the delegation control is unavailable, continue on lab-02-substitute-suggestion yourself. Edit only src/inventory.mjs. The reference implementation in inventory.reference.mjs is available if the time box expires.

Label the fallback honestly in the pull request description: Manual fallback used because Copilot coding agent was unavailable.

Review code, not confidence.

  • Read every application line.
  • Confirm scope stayed narrow.
  • Require green Actions.

Open the final pull request before marking the draft ready. Treat agent output and manual fallback output the same way.

  1. Open Files changed.
  2. Confirm application edits are limited to src/inventory.mjs.
  3. Confirm the only new test file is test/suggestion.test.mjs.
  4. Read every changed application line.
  5. Confirm no workflow, package, server, ownership, or fixture file changed.
  6. Open Checks and wait for all required GitHub Actions checks to pass.

Questions to answer in review

  • Does MED-003 return MED-004 because it is same category and in stock?
  • Does the code sort candidates by SKU before choosing one?
  • Does a suggestion leave stock unchanged?
  • Are unknown-SKU and successful-reservation behavior untouched?
  • Would you reject this pull request if Actions were red?

Checkpoint: the pull request is ready to merge only when the changed-files list is narrow, the review questions have answers, and Actions is green.

Merge only proven work.

  • Green checks are required evidence.
  • Human review accepts responsibility.
  • Chapter 5 consumes this revision.

  1. Request a table partner review if your station requires it.
  2. Resolve any review comments with commits, not hidden local notes.
  3. Merge only after required checks are green.
  4. Return to the Project board and move the issue to the completed column used by your station.
  5. Confirm the issue links to the merged pull request.

The merge commit, issue, project card, Actions run, and review comments are the handoff. Chapter 5 uses the merged revision as the starting point for continuous maintenance.

Stop condition

If Actions stays red or scope drift appears, do not merge. Use the recovery section, repair the branch, and ask for another review.

Recovery and extensions

Recovery keeps the evidence honest.

  • Fix observable symptoms.
  • Keep fallback labeled.
  • Never merge red.

Common blockers

SymptomLikely causeFix
The coaching agent is not in the agent list.The session started outside your station clone, or before you pulled the latest default branch.Run git switch main and git pull in the station clone, confirm .github/agents/ exists, then restart Copilot CLI or reload VS Code from that folder.
The agent writes the requirement for you.The default agent answered instead of the coach, or the prompt asked for a solution.Select the coach explicitly and answer its question. If it still solves the task, switch to the paired fallback.
The agent never produces a draft.It waits for the human gate.Send one message that starts with CONFIRMED: and states your summary in your own words.
A pull request appeared during Step 1.The coach was started as a cloud agent task instead of an interactive chat.Close that pull request without merging, delete its branch, and continue in Copilot CLI or VS Code chat.
The [Backlog] issues are missing.The facilitator has not seeded this station.Tell the facilitator. Continue with the three context files; backlog noise is also described there.
The issue form is missing.You are in this authoring repository, not your station repository.Open your station repository and use the Reservation capability form, not the workshop-change form.
The Project board is not available.The station Project was not created before the event.Keep the issue open, tell the facilitator, and continue. The issue and pull request still preserve the handoff.
Actions did not run after the test commit.The workflow did not trigger, or repository Actions are disabled.Push a small correction to the same branch and open Actions. If Actions are disabled, ask the facilitator before continuing.
The red failure is unrelated to suggestions.The copied test file differs from the artifact.Compare test/suggestion.test.mjs with the artifact and fix the copy before implementation starts.

The final pull request changed too many files.The implementation drifted beyond the issue scope.Revert unrelated files. Keep only src/inventory.mjs and test/suggestion.test.mjs.

Catch up or reset

You ran out of time in Step 1
Stop refining. Open the confirmed business requirement, create the issue from it, and note in the Step 5 comparison comment that the draft was incomplete.
Copilot is still working at the end of the time box
Leave the pull request open. Finish Steps 6 and 7 during the Connect segment, before Lab 3 starts. Merge only when the Step 7 stop condition is met.
You need a fast reset
Close the pull request without merging, delete the branch, and recreate lab-02-substitute-suggestion from the default branch.

Go further
after merge.

  • Probe the coaching agent.
  • Inspect CI evidence.
  • Prepare Chapter 5 questions.

Probe the coach
Ask the coaching agent to “just write the issue.” Note how its instructions and its read-only tool list keep it in the coaching role, then decide which rule you would add to your own agents.
Improve the issue
Add a comment that explains why the substitute rule is deterministic but nonclinical. Keep it short enough for a reviewer to scan.
Audit the check
Open the green Actions run and identify which command executed the Node test suite.
Compare with the reference
Open inventory.reference.mjs and compare it with your merged implementation. Different structure is acceptable when behavior and scope match.
Prepare for Chapter 5
Write one question: how should an automated maintenance loop detect future regressions in this substitute behavior?

A verified handoff is not an agent promise. It is a chain of GitHub artifacts: issue, project card, expected-red test, bounded implementation, green Actions checks, review, and a merged revision that later automation can trust.

Make the work provable.
Then hand it off.
