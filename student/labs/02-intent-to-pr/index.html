Before you start

The handoff is the product.

  • Issue captures intent and boundaries.
  • Tests make acceptance deterministic.
  • Review judges the agent proposal.

Outcome: a merged pull request in your station repository that adds deterministic substitute suggestions to the synthetic reservation API, with GitHub Actions green and a human review confirming the scope.

The merged revision becomes the verified handoff that Chapter 5 consumes. Do not rely on chat history, local notes, or an agent summary as the system of record.

You need

Your station repository
Use the repository URL assigned for your station. You have write access, and the repository already contains the pharmacy service and workflows.
Your team GitHub Project board
Use the project linked from the station instructions. It is where the issue stays visible after delegation starts.
A browser
The core path uses GitHub Issues, Projects, the web editor, Actions, and pull request review. PowerShell commands are optional.
Optional Copilot coding agent entitlement
GitHub Copilot coding agent requires the right plan, policy, and repository enablement. If it is unavailable, use the manual fallback in this guide.

Read the source material first

Open these workshop artifacts before creating the issue. They define the business request, observable contract, decision record, and deterministic acceptance test.

Warning

Synthetic and nonclinical: the catalogue, stock levels, and substitute rule are workshop fixtures. Selecting by category and lowest SKU makes behavior testable. It is not medical or pharmaceutical advice.

Rule

Verification for this lab is GitHub-native: green GitHub Actions checks plus pull request review. Do not use the deleted local lab runner or lab metadata from earlier drafts.

Create the handoff issue

Write the issue as a contract.

  • Outcome first.
  • Acceptance stays observable.
  • Constraints limit the worker.

  1. Open your station repository on GitHub.
  2. Choose Issues, then New issue.
  3. Select Reservation capability.
  4. Copy the title, outcome, acceptance criteria, constraints, and risk from feature-request.md.
  5. Add links to specification.md, decision-record.md, and suggestion.test.mjs.
  6. Create the issue.

Use this title exactly so your table can find the same work:

[Reservation] Suggest an available substitute when stock is zero

Expected result

The issue states that POST /reservations still returns 409 for unavailable stock, adds one deterministic suggestion when eligible, omits it when no candidate qualifies, and never changes stock while suggesting.

The constraints must say that the implementation is dependency-free, synthetic-data only, and bounded to src/inventory.mjs plus the optional new test/suggestion.test.mjs.

Why this matters

An agent must not infer product policy. Outcome, acceptance, constraints, and risk belong in the issue before anyone starts implementation.

Put intent where the team works.

  • The project board shows ownership.
  • Status survives agent handoff.

  1. Open the issue sidebar.
  2. Find Projects.
  3. Add the issue to your team Project board.
  4. Set the status to the intake column used by your station.

If the project field is hidden, use the repository or organization project search from the issue sidebar. Ask your table partner to confirm the card appears on the shared board.

Checkpoint: the issue is on the board before you add code. Delegation starts from visible team intent, not a private branch.

Commit expected red

Prove the gap before fixing it.

  • Create a test branch.
  • Commit expected red.
  • Keep the default branch clean.

  1. In your station repository, create a branch named lab-02-substitute-suggestion.
  2. On that branch, create test/suggestion.test.mjs.
  3. Copy the full contents of artifacts/suggestion.test.mjs into the new file.
  4. Commit the file with Add substitute suggestion acceptance test.
  5. Open a draft pull request from the branch into the default branch.

Expected red

GitHub Actions should run against the draft pull request and show a failing test, because src/inventory.mjs does not yet return a suggestion.

Open the failed check and confirm the failure is about the missing suggestion contract, not syntax, import paths, or unrelated tests.

If Actions is not red

Confirm the file path is exactly test/suggestion.test.mjs, the branch is not the default branch, and the committed file matches the artifact. Fix the test branch before delegating implementation.

Checkpoint: the draft pull request is committed and expected-red. This is visible evidence that the acceptance test detects the current gap.

Delegate and review

Delegate the smallest safe change.

  • Use the issue as context.
  • Bound application edits tightly.
  • Fallback stays honest.

Preferred path — Copilot coding agent

  1. Open the structured issue.
  2. Use the repository control for delegating the issue to GitHub Copilot coding agent.
  3. Paste the bounded prompt below.
  4. Wait for Copilot to open or update a pull request.
Implement the reservation substitute suggestion from this issue.
Use the committed red acceptance test as the proof.
Change only src/inventory.mjs.
Do not edit workflows, package files, ownership, server code, or existing tests.
Keep the service dependency-free and use synthetic data only.
Return one suggestion with sku, name, and available for the first same-category candidate with enough stock, ordered by SKU.
Omit suggestion when no candidate qualifies.
Do not mutate stock when returning a suggestion.
Run npm test and iterate until GitHub Actions is green.

If Copilot opens a separate pull request that does not include the committed acceptance test, do not merge it as-is. Bring the src/inventory.mjs change into your expected-red pull request, or add the committed test to Copilot's pull request, so Actions proves both files together.

Fallback path — no Copilot coding agent entitlement

If the delegation control is unavailable, continue on lab-02-substitute-suggestion yourself. Edit only src/inventory.mjs. The reference implementation in inventory.reference.mjs is available if the time box expires.

Label the fallback honestly in the pull request description: Manual fallback used because Copilot coding agent was unavailable.

Review code, not confidence.

  • Read every application line.
  • Confirm scope stayed narrow.
  • Require green Actions.

Open the final pull request before marking the draft ready. Treat agent output and manual fallback output the same way.

  1. Open Files changed.
  2. Confirm application edits are limited to src/inventory.mjs.
  3. Confirm the only new test file is test/suggestion.test.mjs.
  4. Read every changed application line.
  5. Confirm no workflow, package, server, ownership, or fixture file changed.
  6. Open Checks and wait for all required GitHub Actions checks to pass.

Questions to answer in review

  • Does MED-003 return MED-004 because it is same category and in stock?
  • Does the code sort candidates by SKU before choosing one?
  • Does a suggestion leave stock unchanged?
  • Are unknown-SKU and successful-reservation behavior untouched?
  • Would you reject this pull request if Actions were red?

Checkpoint: the pull request is ready to merge only when the changed-files list is narrow, the review questions have answers, and Actions is green.

Merge only proven work.

  • Green checks are required evidence.
  • Human review accepts responsibility.
  • Chapter 5 consumes this revision.

  1. Request a table partner review if your station requires it.
  2. Resolve any review comments with commits, not hidden local notes.
  3. Merge only after required checks are green.
  4. Return to the Project board and move the issue to the completed column used by your station.
  5. Confirm the issue links to the merged pull request.

The merge commit, issue, project card, Actions run, and review comments are the handoff. Chapter 5 uses the merged revision as the starting point for continuous maintenance.

Stop condition

If Actions stays red or scope drift appears, do not merge. Use the recovery section, repair the branch, and ask for another review.

Recovery and extensions

Recovery keeps the evidence honest.

  • Fix observable symptoms.
  • Keep fallback labeled.
  • Never merge red.

The issue form is missing
Confirm you are in the station repository, not this authoring repository. Use the Reservation capability form, not the workshop-change form.
The Project board is not available
Keep the issue open and tell the facilitator. Continue the lab; the issue and pull request still preserve the handoff.
Actions did not run after the test commit
Push a small correction to the same branch, then open the Actions tab. If repository Actions are disabled, ask the facilitator before continuing.
The red failure is unrelated to suggestions
Compare test/suggestion.test.mjs with the artifact and fix the copied file before implementation starts.
Copilot coding agent is unavailable
Use the manual fallback and label it in the pull request. This is a supported fallback, not a simulation.
The final pull request changed too many files
Revert unrelated files in the pull request. Keep only src/inventory.mjs and test/suggestion.test.mjs.
You need a fast reset
Close the pull request without merging, delete the branch, and recreate lab-02-substitute-suggestion from the default branch.

Go further
after merge.

  • Tighten issue quality.
  • Inspect CI evidence.
  • Prepare Chapter 5 questions.

Improve the issue
Add a comment that explains why the substitute rule is deterministic but nonclinical. Keep it short enough for a reviewer to scan.
Audit the check
Open the green Actions run and identify which command executed the Node test suite.
Compare with the reference
Open inventory.reference.mjs and compare it with your merged implementation. Different structure is acceptable when behavior and scope match.
Prepare for Chapter 5
Write one question: how should an automated maintenance loop detect future regressions in this substitute behavior?

A verified handoff is not an agent promise. It is a chain of GitHub artifacts: issue, project card, expected-red test, bounded implementation, green Actions checks, review, and a merged revision that later automation can trust.

Then hand it off.
