Before you start

Your evidence is the lab.

  • Use the Lab 2 merged pull request.
  • Judge one revision, not a green tick.
  • Authority stays with a named person.

Outcome: a pull request in your station repository that adds a completed release decision, plus an owned issue update that records the next bounded loop decision.

You need

Your station repository
Use the repository assigned for this workshop. You have write access and the earlier labs produced the evidence you judge here.
Earlier lab artifacts
Use your Lab 2 merged pull request, Lab 3 governance decisions and CODEOWNERS, Lab 4 workflow and security evidence, and the Lab 1 owned issue.
A browser
The core path works in GitHub. PowerShell and the gh CLI are optional conveniences.

Rule

Do not use supplied evidence packets. This capstone is about your station repository. If evidence is missing, stale, ambiguous, or bound to the wrong commit, record that defect and block or escalate.

Templates

Open the evidence checklist and the release decision template. The checklist tells you what to verify. The template is intentionally empty; your repository history supplies the answers.

Important boundary

This lab creates a release-readiness decision. It does not deploy production, approve an environment, or override a release owner. Consistent evidence can support a recommendation; only a named person with authority can approve release.

Collect and bind evidence

Start with the change.

  • Find the Lab 2 merged pull request.
  • Record head and merge revisions.
  • Choose the revision you will judge.

Open Pull requests, select Closed, and open the Lab 2 pull request for the reservation suggestion feature.

Record these values in your notes before judging anything:

  1. Pull request number and title.
  2. The pull request head SHA reviewers saw.
  3. The merge commit SHA on the default branch, if the pull request merged.
  4. The revision your release-readiness decision will judge.

PowerShell option

If you use the gh CLI, run this from any folder:

gh pr list --state merged --limit 20
gh pr view <number> --json number,title,headRefOid,mergeCommit,reviews,statusCheckRollup,closingIssuesReferences

Use the web UI if the CLI is not authenticated. Do not spend time repairing tooling.

Checkpoint

You can say, "I am judging this revision", and point to the exact SHA. If you cannot name the SHA, you are not ready to inspect green checks.

Green is not enough.

  • Read which commit each check used.
  • Name every required deterministic check.
  • Wrong revision is a defect.

On the pull request, open Checks and Conversation. For each required or relied-on signal, record the name, conclusion, run link and commit SHA.

Verify at least these evidence classes:

Deterministic checks
Build, test, workflow contract, dependency review, code scanning, secret protection, or the Lab 4 hardened delivery checks your station uses.
Human review
The approving review, reviewer identity, timestamp, and the commit shown when that approval was made.
Governance
The CODEOWNERS entry or Lab 3 decision that explains who should review this area.
Security findings
Any open, dismissed, or remediated finding that affected the release decision.

Warning

A passing check for a different commit proves nothing about the revision you are judging. Record it as wrong-revision evidence, not as partial credit.

Expected result

You have a short evidence table. Every row either names the chosen revision, maps to it through a trusted GitHub relationship, or is listed as a defect.

Separate readiness from outcome.

  • Pre-release evidence supports a decision.
  • Deployment evidence observes what happened.
  • Neither replaces human authority.

Open Actions and Deployments or Environments, if your station has them. Search for records connected to the Lab 2 pull request or your chosen revision.

Classify what you find:

Pre-release readiness evidence
Packaging, test deployment, release workflow inputs, environment approval request, or dry-run evidence before a release owner decides.
Post-deployment outcome evidence
A deployment record, health check, rollback, or incident signal after an approved release happened.
No deployment evidence yet
A valid state before release. Do not invent a deployment record. Record whether the decision can still be a readiness recommendation.

If a deployment record exists, verify which commit it names. If it names a different commit than the one reviewed, the deployment may be real, but it is not evidence for this release decision.

Write the decision

Write the judgment down.

  • Name relied-on evidence.
  • Name every defect.
  • Choose release, block, or escalate.

Create a branch named capstone-release-decision. Copy the release decision template into your repository as:

docs\decisions\lab-05-release-decision.md

Complete every heading. Keep the decision concise and auditable. Another engineer should be able to reconstruct your reasoning without reading an agent chat.

Decision vocabulary

Release
The evidence is complete for a release-readiness recommendation. A named release owner still approves the actual release.
Block
Required evidence is absent, failed, stale, or bound to a different revision.
Escalate
The evidence is ambiguous, authority is unclear, or a person outside your table must decide.

Rule

Do not write "all checks passed" unless you can name the checks and the commit they ran against. Specific evidence is stronger than confident wording.

Make the decision durable.

  • Commit it as repository evidence.
  • Review the decision like code.
  • Merge only when it is clear.

Commit the completed decision to your branch and open a pull request. Title it:

Record Lab 5 release decision

In the pull request description, include three bullets:

  1. The revision under review.
  2. The decision: release, block, or escalate.
  3. The named owner for the next decision.

Ask your table partner to review one thing: whether every relied-on evidence item names the same revision or is explicitly marked as a gap.

Merge the pull request only after the decision reads like a durable record, not a classroom worksheet.

Close the loop

The next run must earn work.

  • Open the Lab 1 owned issue.
  • Read prior state before acting.
  • No-op is valid when justified.

Open the issue created or updated by the Lab 1 repository-pulse workflow. Search open and closed issues for the workflow marker or title if needed.

Add a comment that answers four questions:

  1. What release decision did the capstone pull request record?
  2. What evidence or defect should the next run consume?
  3. Should the next run no-op, wait, escalate, or retry?
  4. Who owns the next human decision?

Use the bounded vocabulary

No-op
Use when the same accepted evidence is already recorded and no new work is justified.
Wait
Use when a named product, review, or release owner must decide before another model run.
Escalate
Use when authority is unclear, evidence is missing, or the allowed repair path is exhausted.
Retry
Use only for one specific trusted failure when a repair attempt remains.

Checkpoint

A justified no-op is a successful governed outcome. It says the loop read state, found no eligible work, and avoided duplicate agent activity.

Consistency is not authority.

  • Evidence supports a recommendation.
  • People hold release authority.
  • The loop stops when ownership says stop.

Before you finish, say this boundary out loud at your table:

Consistent evidence can make a release-readiness recommendation defensible. It does not grant release authority. The named release owner decides.

Then verify your repository contains two durable records:

  1. The merged pull request that records the release decision.
  2. The Lab 1 owned issue comment that records the next loop decision.

This closes the day's story: intent became a proposed change, evidence constrained it, governance named owners, and the next agentic action is bounded by persisted state.

Recovery and extensions

Recover honestly.

  • Missing evidence is a valid finding.
  • Do not invent a release record.
  • Escalate when authority is unclear.

You did not finish Lab 2
Use the latest merged pull request in your station repository as the revision source, and mark the missing Lab 2 reservation evidence as a defect. Your likely decision is block or escalate.
Your pull request never merged
Judge the pull request head SHA. Record that no default-branch merge or deployment evidence exists, then decide whether that blocks release readiness.
Checks are hard to find
Open the pull request's Checks tab and the linked workflow run. If a required check cannot be found, list it as missing evidence.
No deployment record exists
Do not treat absence as failure automatically. State whether deployment outcome evidence is not yet expected, or whether your station policy required pre-release deployment evidence.
The Lab 1 issue is missing
Create or reopen a repository issue named Repository pulse next decision, explain why the owned issue is missing, and record the next decision there.

Troubleshoot the claim.

  • Find the SHA first.
  • Then interpret the signal.
  • When unsure, escalate.

Common blockers

SymptomLikely causeFix
A check is green but shows no obvious SHA.The commit is recorded on the workflow run, not on the check summary.Open the workflow run details. GitHub records the event, branch, actor, and commit near the run summary.
A review predates the latest commit.Commits were pushed after the approval.Record the approval as stale unless repository policy dismissed stale approvals or a later approval exists.
CODEOWNERS does not cover the changed file.The ownership map has a gap for that path.Record a governance defect. The correct decision may be escalate to the repository owner.
An agent comment says the feature is ready.Reasoning output is being read as evidence.Treat it as advisory. Only deterministic checks, review records, and named owners can support the decision.
Your table disagrees about the decision.The evidence supports more than one reading.Write both interpretations in the defects section and escalate to the named release owner.

Extend after the core path.

  • Compare two pull requests.
  • Draft a required-check policy.
  • Improve the loop contract.

Compare revisions
Pick another merged pull request and repeat the SHA-binding exercise. Notice which controls are reusable and which are change-specific.
Draft a policy
Write one required-check rule your station should enforce before release readiness, and name the owner who may change it.
Improve recurrence
Propose one field the Lab 1 owned issue should persist so a future run can no-op without rereading unrelated history.
Practice escalation
Rewrite your decision as an escalation memo for a release owner with only three facts and one question.

The governed loop closes when real evidence is bound to a revision, defects are named, authority is explicit, and the next action is bounded by state instead of model momentum.
