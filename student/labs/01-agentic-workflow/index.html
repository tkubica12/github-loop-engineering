Before you start

One workflow. Four edits.
One reviewable change.

  • Tools and permissions must describe the same scope.
  • Budget is part of the contract.
  • A green check is the proof, not your opinion.

Outcome: a merged pull request in your station repository that narrows the repository-pulse automation to issue review only, at a lower budget, with its compile check green.

You need

Your station repository
The URL was sent with your preparation message. You have write access to it. Everything in this lab happens there.
A browser
The whole lab can be completed in the GitHub web editor. A local clone and the gh CLI are optional.
Nothing else
No local Node.js, no extension and no model entitlement are required to finish the core path.

Warning

Product state: GitHub Agentic Workflows are public preview. Steps 1 to 5 are ordinary Git and Actions work and always complete. Step 6 runs the preview engine; if it is not enabled for your station, use the recorded run linked in Recovery and continue.

Starting state

Your repository already contains .github/workflows/repository-pulse.md. The frontmatter is the contract; the prose below it is the instruction. As shipped, the contract is deliberately too wide.

Boundary, key, and value as shipped

Trigger

Key: on

As shipped: workflow_dispatch — a person starts it.

Read scope

Key: permissions

As shipped: contents, issues, pull-requests, actions, all read.

Model access

Key: copilot-requests: write

As shipped: Inference through the per-run token. This is not permission to write repository content.

Network

Key: network

As shipped: defaults — an allow-list, not open egress.

Write scope

Key: safe-outputs

As shipped: Owned create-issue and update-issue, maximum one of each per run.

Agent budget

Key: timeout-minutes, max-ai-credits

As shipped: 10 minutes and 100 AIC. The threat detector has its own 20 AIC cap.

The agent never receives a general-purpose write token. Those two safe-output types are the only ways anything leaves the run. The caps are per output type and per run — they are not one global transaction, and they do not deduplicate across runs.

Narrow the contract

Start on a branch.

  • The default branch is protected.
  • Review is where the change is judged.

In your station repository, open the branch selector, type the branch name and choose Create branch:

narrow-repository-pulse

Prefer the command line? This is equivalent:

gh repo clone <your-station-repository>
cd <your-station-repository>
git switch -c narrow-repository-pulse

Rule

Do not commit to the default branch. It is protected, and Chapter 3 will show you exactly which control rejects the push and who owns that control.

Align tools with permissions.

  • Remove the scopes you no longer read.
  • Cut time and inference budget.
  • Keep the safety invariants untouched.

Your team has decided this automation should review issues only, and cost less. Open .github/workflows/repository-pulse.md on your branch and make exactly these four edits.

Edit 1 — Match tools to permissions

Delete pull-requests: read and actions: read from permissions. Under tools.github, replace toolsets: [default] with:

toolsets: [repos, issues]

A toolset wider than the permission grant is a silent contradiction. Reviewers cannot tell what the automation is actually allowed to touch.

Edit 2 — Reduce the time budget

timeout-minutes: 5

Edit 3 — Reduce the inference budget

max-ai-credits: 40

Edit 4 — Narrow the instruction

Replace the opening instruction line with:

Review issues opened or closed in the previous seven days. Read repository files only to explain issue context.

Then replace the bullet - failing or cancelled default-branch checks; with:

- issues opened or closed in the period, each linked to its artifact;

Rule

Do not change these. Keep copilot-requests: write — it grants model access, not repository writes. Leave the manual trigger, the Copilot engine, network: defaults, both owned safe-output limits of one, the concurrency group, and the untrusted-input paragraph exactly as they are. Keep the threat detector at 20 AIC with continue-on-error: false: a failed security review must stop the run, not warn and proceed.

Commit to your branch with a message that states the intent, for example Narrow repository pulse to issue review.

Prove it on GitHub

The check is the evidence.

  • Compilation validates the contract.
  • Red tells you what is still wrong.

Open a pull request from narrow-repository-pulse into the default branch. The Workflow contract check starts automatically. It recompiles the agentic workflow and fails if the contract and the compiled lock disagree.

Checkpoint — what green means

When the check passes, the pull request shows a recompiled .lock.yml in the diff. Read it. This is the deterministic artifact that Actions will actually execute; the Markdown you edited is the source it was generated from.

If the check is red

Open the failed check and read the first error. The three usual causes are a toolset that no longer matches the permissions, a YAML indentation slip in the frontmatter, or an edit made below the closing --- when it belonged above it. Fix it on the same branch and push again.

Request a review from your table partner. Ask them one question: after this change, what is the worst thing this automation can still do? The answer should be "create or update one issue it owns". If they cannot tell from the diff alone, the contract is not narrow enough yet.

Merge the pull request once the check is green.

One run. One owned issue.

  • Per-run caps are not deduplication.
  • Recurrence needs identity and prior state.

Go to Actions, select Repository pulse and choose Run workflow. It is a manual trigger, so nothing happens until a person asks for it.

When the run finishes, open the issue it created. Check three things:

  1. The issue is owned by the workflow — it carries the <!-- workshop-pulse:v1 --> marker.
  2. It links each finding to an artifact, so a reader can verify the claim rather than trust it.
  3. It ends with a next decision, not just a summary.

Now find what is missing

Run the workflow a second time without changing anything in the repository.

A second issue update is produced, even though nothing actionable changed. The per-run cap did its job — it bounded the blast radius of one run. It did not make the automation continuous. That needs three things the contract does not yet have:

Stable work identity
Something that says "this is the same piece of work as last time", independent of the run number.
Prior-state read-back
Reading what the previous run concluded before deciding to act again.
An explicit next decision
A justified no-op is a valid, accountable outcome. Silence is not.

Chapter 5 closes exactly this gap. Carry the observation with you.

Recovery and extensions

Recovery is planned.

  • The reference contract resets the edits.
  • Steps 1 to 3 are the graded path.

You ran out of time on the edits
Copy the reference contract over your file, commit, and continue from Step 3. You still see the check, the review and the run.
The preview engine is not enabled for your station
Steps 1 to 3 still complete and are the graded part of this lab. For Step 4, read the recorded run output in the full-day guide and answer the same three questions against it. Say out loud that you are reading a recording, not your own run.
You edited the wrong branch
Nothing is lost. Create the branch again from the default branch and redo the four edits; they take two minutes the second time.
You want to start over completely
Delete your branch and its pull request. The default branch is untouched, because it is protected.

Go further
once it is merged.

  • Break the contract and read the check.
  • Argue whether it deserves a schedule.

Break it on purpose
Add contents: write to permissions and push. Read what the compile check says, and decide whether you would approve that pull request.
Tighten the trigger
Add a schedule alongside workflow_dispatch. Then argue the other side: what does a schedule create that a manual trigger does not, and does this automation currently deserve it?
Read the lock
Open the generated .lock.yml in full and find where your budget values ended up. Anything not expressed there is not enforced at runtime.

A narrow contract is what makes an automation reviewable. Tools, permissions and budget must tell one consistent story, and a deterministic check — not an opinion — decides whether the change is safe to merge.

Bound it first.
Then let it run.
